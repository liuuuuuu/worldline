# ADR-0005 · 静态快照 + 动态镜像发现，应对上游不可靠

- **状态**：已采纳
- **日期**：2026-10-08
- **决策者**：Alex / Ace

## 背景

上一轮汇报里列了三条与上游可用性相关的风险：

| # | 风险 |
|---|---|
| 2 | 首次加载 ~130s（151 个请求） |
| 3 | `de1` 单点依赖，它挂了就没有备选 |
| 4 | 上游数据质量差（spam 电台名） |

动手前先量了三件事，结果推翻了我原本的判断。

### 发现一：其余镜像不是"连不上"，是"已经下线"

原本以为 `nl1`/`at1`/`fi1` 只是本机网络不可达。查 `/json/servers`（0.6s，123 字节）：

```
de1.api.radio-browser.info | 91.98.4.78
de1.api.radio-browser.info | 2a01:4f8:1c1d:699::1
```

**只有 `de1` 一个节点，出现两次（IPv4 + IPv6）。** 代码里那份硬编码镜像列表写的时候就已经过期了。
所以正确的修法不是"换一个镜像"，是**动态发现**。

### 发现二：小请求快得不成比例

| 请求 | 体积 | 耗时 |
|---|---|---|
| 250 行全局页 | ~317 KB | ~30s |
| 20 行单国请求 | ~25 KB | 1.3–4.1s |

这条在 ADR-0004 里已经用过一次（按国家配额）。这次它决定了"快照生成只要 19 秒"。

### 发现三：spam 名称是极少数

抽样看下来，绝大多数名称是正常的。真正离谱的只有极少数，比如那条 230 字符的
`- DJ & CLUB CHARTS ---> Club Classics, Festival-Hits, ...`。

**所以过滤器要保守。** 砍掉一个电台就是砍掉地理覆盖——正是 ADR-0004 要保护的东西。

## 决策

### 1. 静态快照（`npm run snapshot`）

构建期生成 `public/stations.snapshot.json`（1793 站 / 142 国 / 991 KB / 生成耗时 19s）。

- 启动时**先读快照**，约 100ms 就能把地球仪填满
- 实时按国家拉取在后台跑，到达后**替换**快照数据
- 快照数据是**临时的**，不参与最终结果——否则陈旧条目会随版本累积成幽灵

快照里存的是**上游原始字段名**，不是我们的 `Station` 结构。这样映射只有一份
（`toStation`），校验也只有一份（`parseRadioBrowserStations`）。裁剪成自有结构能省约 30%
体积，代价是第二份可能悄悄漂移的映射代码——不划算。

### 2. 动态镜像发现 + 粘性记忆

- 启动时读 `/json/servers`，拿实时节点列表（缓存 24h）
- 优先级：上次成功的镜像 → 实时发现的 → 硬编码兜底
- 某次请求成功后，把该镜像移到队首并持久化，同一次加载里的后续请求直接跳过死节点
- 调用方显式传了 `mirrors` 就完全不做发现和重排——"给定了就用这些"是应有之义

### 3. 名称质量过滤（保守）

只拦四种明确特征：箭头链（`--->`）、超过 80 字符、逗号堆砌（≥6 个且 >60 字符）、
管道符堆砌（≥4 个且 >30 字符）。

`Ö1 | ORF | HQ`、`WALM - Old Time Radio`、`Radio Paradise Main Mix (EU) 320k AAC` 全部放行。

另外提供 `shortenStationName()` 做显示截断——**长名字是显示问题，不该靠删数据解决**。

## 后果

**正面**
- 冷启动首个图钉：**5.8s**（其中 ~5.5s 是 WebGL 驱动冷启动，见下）
- 同进程第二次加载：**278ms**
- 所有镜像都挂时仍有完整地球仪，而不是错误页
- 覆盖国家数 142（与实时数据一致）
- 上游改字段名时 `rejectedStations` 会上报；目录里出现垃圾时 `filteredStations` 单独上报——**两者分开计数**，否则一次 schema 破坏会淹没在正常噪声里

**负面**
- 快照 991 KB 进仓库、进分发产物
- 快照会随版本陈旧（缓解：24h 缓存 + 每次启动后台刷新）
- 生成快照依赖 `de1` 当时活着

## 一个重要的测量教训

第一次测"首个图钉"得到 4.0s，第二次 7.1s，来回跳。原因是**测量脚本自己在 `Page.navigate`
之后 `sleep(3000)`**，给这个数字设了 4s 下限——测的一直是"3s 之后还要多久"，不是"多久"。

改成立刻开始 250ms 轮询后：冷 5.8s / 热 278ms。

**差点把一个测量假象写进文档。**

## 关于那 5.8s

同一个浏览器进程里，第二次加载只要 278ms。所以 5.8s 基本全是
**WebGL 驱动 + 着色器首次编译**，不是我们的代码。桌面应用（Tauri）进程只启动一次，
用户只在第一次启动时付这笔钱。

仍未优化、留待 P6 的：把 4096×2048 贴图绘制从启动路径里挪开（已完成一半——
陆地贴图已延到首帧之后，占位贴图已降到 512×256）。
