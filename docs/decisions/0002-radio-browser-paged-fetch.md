# ADR-0002 · Radio Browser 分页串行拉取，而不是一次拉大响应

- **状态**：已采纳
- **日期**：2026-10-07
- **决策者**：Alex / Ace

## 背景

P1 的原计划是：一次请求 `?has_geo_info=true&hidebroken=true&limit=3000`，10 秒超时，拿回 3000 个带坐标电台。

实测（2026-10-07，真实浏览器 + 直连，非代理）：

| 请求 | 耗时 | 体积 |
|---|---|---|
| `limit=100` | 2–7s | 125 KB |
| `limit=250` | **14–29s** | 317 KB |
| `limit=1000` | **80–86s** | 1.25 MB |
| `limit=3000` | **>120s，从未完成** | — |
| 同样的 `limit=300` 两次 | 4s / 25s | 抖动 6 倍 |

并且：**5 个官方镜像只有 `de1` 可达**（`nl1`/`at1`/`fi1`/`all` 全部 `HTTP 000`）。

**「一次拉 3000 条 + 10s 超时」在物理上不可能成立。**

## 考虑过的选项

| 选项 | 结论 |
|---|---|
| 保持一次大请求，只调大超时到 120s | ❌ 首次加载两分钟，且单次失败就全盘皆输 |
| 降低目标到 100–300 条 | ❌ 地球仪上光点太稀疏，失去「世界」的感觉 |
| **分页 + 逐页缓存 + 渐进渲染** | ✅ 采纳 |
| 打包一份静态快照进仓库 | 备选，见「后果」 |

## 决策

**分页拉取，每页 250 条，串行，逐页独立缓存 24h，结果渐进交付。**

关键的第二条决策：**并发度设为 1（串行）**。

这一点反直觉，但是实测结论：

| 并发数 | 结果 |
|---|---|
| 3 页并发 | 只有 1 页成功，3 页超时 |
| **串行** | **4 页全部成功，0 失败** |

上游（或到上游的链路）对并发连接限流。**并行不买来吞吐，只买来失败。**

## 后果

**正面**
- 首次加载 97.7s，**缓存后 106ms**（IndexedDB，快约 900 倍）
- 单页失败不再拖垮整体：`meta.failedPages` 上报，UI 明确显示「3/4 页失败」而不是假装完整
- 页面可以在第一页到达时就渲染出 250 个光点，而不是干等两分钟
- 每页独立缓存 → 后续增量更新只需重取失效的页

**负面**
- 首次加载接近 100 秒，对「打开就能玩」的期望是硬伤
- 实现复杂度显著上升（分页、去重、部分失败、进度回调）
- 缓存按 `limit+offset` 分片，改 `pageSize` 会导致缓存全部失效

**缓解与后续**
- P2/P3 期间不需要重新拉取，缓存有效
- **P6 之后应考虑打包静态快照**：目录变化很慢（24h TTL 已经说明这一点），
  在构建期生成 `stations.snapshot.json` 随应用分发，运行时只做后台增量刷新。
  这能彻底消灭「首次 100 秒」的问题，且让应用在断网时依然可用。
- 用 `has_geo_info=true` 让上游做过滤，避免下载 83% 用不上的无坐标电台
