# ADR-0006 · http 流转服务端转发（混合内容）

- **状态**：已采纳
- **日期**：2026-10-08
- **决策者**：Alex / Ace

## 背景

约有一部分电台只有 `http://` 流。页面在安全上下文（HTTPS 页面、Tauri 的自定义协议）里
播放它们会被浏览器以混合内容拦截。

**先量了比例，结果和预期差很多：**

| 范围 | http-only 占比 |
|---|---|
| 快照全部 1793 站 | **23%**（419 站） |
| 票数前 50 | **16%**（8 站） |

我最初参考的经验值是 71%。**那个数字不适用于我们的数据集**——它来自"按票数排前 300 的
全集"，而我们的样本是"每国前 20"，大台（BBC、Radio Paradise 之类）的比例本来就低。

23% 仍然值得做：419 个电台是用户真会点到的，而且按票数排序时它们更容易被点到。

## 决策

**做转发，但绝不做成通用代理。**

一个"你传 URL 我就取"的转发端点等于把服务器变成打内网的跳板。三条约束缺一不可：

1. **主流的请求用业务 id，不用 URL。** 客户端传 `?uuid=<stationuuid>`，
   服务端自己在快照里查真实地址。调用方**无法构造任意请求**。
2. **HLS 子资源才传 URL**（分片在别的域名上），但每一个都过 SSRF 守卫。
3. **重定向自己跟，每一跳重新校验。** 用 `redirect: 'follow'` 的话，一个公网 URL
   可以 302 到 `169.254.169.254`——这正是要防的。

### SSRF 守卫

`src/relay/ssrf.ts`，纯函数、无 `node:` 依赖，因此可以用和其他代码一样的 vitest 环境测。

拦截：回环、私网（10/8、172.16/12、192.168/16）、链路本地（**含云元数据 169.254.169.254**）、
CGNAT（100.64/10）、组播与保留段、IPv6 ULA（fc00::/7）、文档段（2001:db8::/32）、
以及 **IPv4 映射的 IPv6**（`::ffff:127.0.0.1` 是穿了马甲的 loopback，要拆开再判一次）。

两条容易写错的：
- **判解析后的 IP，不是域名。** `evil.example.com` 可以解析到 `10.0.0.5`。
- **判每一条 A 记录，不是第一条。** 一个域名同时有公网和私网记录时，取 `records[0]` 是抛硬币。

协议只放 http/https；URL 里带凭据直接拒（会泄漏进日志）。

### 超时只限握手

直播流是长连接。给整个响应设超时会几十秒后掐断播放。
12s 定时器在响应头到达后就清除，body 想流多久流多久。

### HLS 必须重写清单

`m3u8` 不是音频，是**指向更多 URL 的清单**。只转发清单本身，分片请求照样走 HTTP、照样被拦。
三类都要重写：裸 URL 行、`URI="..."` 属性（`EXT-X-KEY` 解密密钥 / `EXT-X-MAP` init 段 /
`EXT-X-MEDIA`）、以及相对路径**相对清单自身的 URL** 解析（不是相对页面）。

## 实测验证

| 用例 | 结果 |
|---|---|
| 真实 http 台（Radio Paradise） | **HTTP 200 + 1,169,588 字节真实音频** ✅ |
| HLS 清单 | 200 + `application/vnd.apple.mpegurl`，子清单已改写为 `/api/stream?u=...` ✅ |
| 相对路径 `chunklist.m3u8` | 按清单自身 URL 正确解析 ✅ |
| `u=http://169.254.169.254/latest/meta-data/` | **403 private-address** ✅ |
| `u=http://127.0.0.1:8080/` | **403 private-address** ✅ |
| `u=http://10.0.0.5/` | **403 private-address** ✅ |
| `u=file:///etc/passwd` | **403 protocol-file** ✅ |
| `u=http://localhost/` | **403 blocked-hostname** ✅ |
| 未知 uuid | 404 ✅ |
| 缺参数 | 400 ✅ |

### 一个测试方法上的坑

第一轮用 `sed` 手工 URL 编码去测，`169.254.169.254` 和 `127.0.0.1` 两个用例返回了 502
而不是 403，看起来像守卫失效。查了半天守卫函数本身——**它是对的**。

问题在测试命令：这台机器上 `sed` 在命令替换里不可靠（同一脚本第二次运行直接报
`unterminated 's' command`），那两个 URL 被编码坏了。

改用 `curl -G --data-urlencode` 后，五个用例全部正确 403。

**教训：手工拼 URL 做安全测试，本身就是一个会误报的环节。** 用工具自带的编码。

## 后果

**正面**
- 419 个 http-only 电台在安全上下文里可播
- 主流的请求无法被用于 SSRF
- 转发可以整体关掉（`WORLDLINE_STREAM_RELAY=0`）——它唯一显著的成本是**服务器带宽**，要让部署者自己决定

**负面**
- 增加一跳，首字节延迟变高
- 部署者要付带宽
- 上游本身已死的台仍会 502（实测 3 个里 1 个）——这是目录质量问题，不是转发问题，P4 要靠"坏台自动跳过"消化
