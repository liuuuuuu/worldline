# ADR-0001 · 用 three.js 直接搭场景，而非 globe.gl

- **状态**：已采纳
- **日期**：2026-10-07
- **决策者**：Alex / Ace

## 背景

「探索态」需要在屏幕上渲染一颗摆在桌面上的**实体地球仪**：黄铜子午环、木质底座、哑光纸质地图贴面、约 3000 枚图钉，外加桌面、环境光与真实投影。

最初方案（由架构调研给出）推荐 `globe.gl`，理由是它内置 `pointOfView({lat, lng, altitude}, ms)`，天然支持"俯冲降落"的相机动画，且万级点云无压力。

## 考虑过的选项

| 选项 | 优点 | 缺点 |
|---|---|---|
| **globe.gl** | 开箱即用；`pointOfView` 直接做飞行动画；点云性能好 | 只能渲染**写实球体**。它是 `three-globe` 的封装，材质与几何被固定，难以插入黄铜环、木底座、桌面、自定义 shader |
| **three-globe** | 比 globe.gl 底层，可控性稍高 | 仍是"地球仪组件"，不是通用场景；要加非球体几何仍需绕开它的抽象 |
| **three.js 直接搭建** | 完全可控：任意几何、材质、光照、后期、自定义 shader | 相机飞行动画要自己写；代码量更大 |

## 决策

**用 `three.js` 直接搭建场景。**

理由：

1. **物件框架是产品的核心，不能被封装挡住。** 「实体地球仪摆在桌上」需要球体之外的黄铜环、木底座、桌面平面、投影——这些都不是"地球组件"的职责。
2. **P5 的核心是自定义 shader。** 「纸面 → 实景」的过渡需要自己写 fragment shader 混合两套贴图。`globe.gl` 的材质是内部封装的，硬塞 shader 会变成和库搏斗。
3. **相机动画并不难。** `lat/lng/altitude` → 笛卡尔坐标 + easing，约 20 行代码。为了省这 20 行而放弃整个场景的控制权，不划算。

## 后果

**正面**
- 场景完全可控，P5 的 shader 过渡没有技术阻碍
- 材质/光照/后期可以按 `docs/VISUAL.md` 精确调
- 未来接入"声音驱动的壁纸"（P8）时，需要把音频数据灌进 shader uniform，这在自建场景里是自然的

**负面**
- 相机动画、点云拾取需要自己实现（P3 的工作量增加）
- 失去 `globe.gl` 的开箱优化

**缓解**
- 图钉用 `InstancedMesh` 保证 3000 枚的性能
- 相机动画封装成独立的 `scene/camera.ts`，便于单测 easing 逻辑
- 可以借鉴 `three-globe` 的 shader 写法，但不受其架构约束
